### How the layers fit

- **One thread-local, in C.** `robigo_cg` (`robigo-rtcore/src/capi.c`,
  initial-exec) names the isolate's C globals block (`CGlobals`,
  `include/robigo_capi.h`, layout checked against Rust when an isolate is
  made). `Cx::call_out` sets it for every native entry and restores it
  after, so several isolates share a thread one native call at a time and
  run on several threads at once (L6). Rust reads it through two C
  accessors; under Miri, which runs no C, a Rust `thread_local!` with the
  L6 marker stands in.
- **GNU R's public headers, unedited, plus robigo's `Rinternals.h`.**
  `crates/robigo-rtapi/include/Rinternals.h` includes GNU R 4.6.2's own
  (`#include_next`), then makes `R_NilValue`, `R_GlobalEnv`, the symbol
  shortcuts, ... macros over `robigo_cg`, as §11 says. C that declares
  `extern SEXP R_NilValue` itself fails to load with "undefined symbol"
  (the crutch's ABI manifest, §10, is for that). `R_NaReal` and the other
  numeric constants are immutable process data. `Rconfig.h` and
  `Rversion.h` are 4.6.2's generated ones, checked in.
- **Exports by kind** (`robigo_rtapi::EXPORTS`, 139 entries):
  - *machine entries* for everything that may collect or exit:
    `entry!` generates, per argument-count class (0 to 5 integer-class
    arguments), a naked stub that pushes rbp, rbx, r12-r15 below its return
    address and passes the lowest address to the Rust body, which closes
    the caller's C segment there (`robigo_rtcore::enter_export`). No Rust
    frame is in a segment. A test reads each entry's first ten bytes
    (`push rbp ... push r15`) and checks every export GNU R's same function
    allocates in is an entry or C over entries.
  - *C* (`api.c`) for the hot accessors (`TYPEOF`, `LENGTH`, `INTEGER`,
    `CAR`, `VECTOR_ELT`, `SET_VECTOR_ELT`, `PROTECT`, ...) over robigo's
    object layout (checked against robigo-heap's), their error paths
    calling entries from a C frame; the variadic functions (`Rf_error`,
    `Rprintf`, ...); and `R_UnwindProtect` composed as GNU R composes it:
    the context and the protected call are an entry's, the cleanup is
    called from C, so a cleanup that leaves by its own `longjmp` (cpp11)
    skips C frames only. A test compiles `api.c` with GNU R's
    `Rinternals.h` forced in: every definition matches GNU R's prototype.
  - *leaves* (Rust, no capability that can collect): the barrier store,
    `Rprintf`'s console write, `R_ReleaseObject`, `vmaxget`/`vmaxset`.
- **Rooted arguments and allocation parity** (§3 item 6, L8): an entry's
  `SEXP` arguments are roots of its scope (`entry::CArg`), marked as seen
  by C under `ROBIGO_GC_MOVE=1`, and so is every object returned to C (by
  entries and by `api.c`'s accessors). An export collects on entry when
  due (`Safepoint::Export`) only on the paths where GNU R's function
  allocates: `install` of a known name, `mkChar` of a cached string,
  `ScalarLogical` (GNU R's shared `R_TrueValue`/`R_FalseValue`/
  `R_LogicalNAValue`, now per isolate), `setAttrib` replacing an attribute
  and `defineVar` of a bound name allocate nothing.
- **C state in contexts** (the foreman's decision on C2's question):
  `begincontext` saves the protect stack's top (`cstacktop`), `R_VStack`
  (`vmax`) and the C segments' state (open top, routine, innermost closed
  segment: robigo's extension of `RCNTXT`, `Defn.h`); a stop or landing
  restores all three (`Cx::restore_c_state`), as GNU R restores
  `R_PPStackTop`. With `R_UnwindProtect` composed in C, no export skips
  its reopen in the tests; the restore covers a `longjmp` that would.
- `.Call` (dotcode.c: `resolveNativeRoutine` for a name and `PACKAGE`,
  `check_retval`, eval.c's `check_stack_balance` and `vmaxset`) and
  `dyn.load` (Rdynload.c: `GetFullDLLPath`, `AddDLL` with GNU R's `dlopen`
  flags, `Rf_MakeDLLInfo`; an `R_init_<pkg>` says registration is not
  implemented yet) are rtapi's builtins; the `robigo-rt` binary moved to
  `robigo-rtapi`, above the API, and links with `-rdynamic`. C finalizers
  run in robigo-rt's `fin.rs` (GNU R's raw-vector `MakeCFinalizer`), which
  now suspends interrupts while a finalizer runs, as 4.6.2's
  `R_RunWeakRefFinalizer` does. Also added: `.Platform`
  (`Init_R_Platform`), `.Internal(gctorture())`, `.Internal(matrix())` and
  `MatrixSubset` with the matrix case of `DropDims` (`gc()`'s R code needs
  them), six-argument entries' object arguments marked as seen by C (H3's
  follow-up).

### Proofs (`cargo test --release -p robigo-rtapi --test capi`, 19 tests)

Package C (`tests/support/capi_test.c`) built as a package is, called
through `.Call` in a session with base loaded; each passes also under
`ROBIGO_GCTORTURE=1` (with `ROBIGO_GC_STATS=check`), `ROBIGO_GCTORTURE=1
ROBIGO_GC_MOVE=1`, and `ROBIGO_GC_PIN_REPORT`.

| case | result |
|---|---|
| E8 1, `Eval` and `Bc`: `f`'s `on.exit` catches its own error (via `R_ToplevelExec` in C) during the unwind of `f`'s error; `f` evaluated from C | the outer error reaches the catcher; "inner caught" |
| E8 2, both: an `R_UnwindProtect` cleanup catches an error of its own | the original error resumes; cleanup saw `jump = TRUE` |
| E8 3, both: `R_ExecWithCleanup`'s cleanup when its body errors | runs before the jump, the routine's frame intact |
| nested native re-entry: C → R → C, 31 levels, a full `R_gc()` in each, with and without gctorture | every level's vector intact (sum 62,496); protect stack balanced |
| cpp11's `unwind_protect` (cleanup `longjmp`s past `R_UnwindProtect`, then `R_ContinueUnwind`), 20 times, both profiles | error arrives; protect stack as before; later collections clean |
| `pin_premature` (7 functions) under gctorture, both profiles | all FALSE, as GNU R |
| `pin_extbuf` | TRUE TRUE, as GNU R |

### The cost of a crossing

Instructions per iteration, callgrind, N vs 2N in a closure's loop
(`scripts/idiom-vs-r.py 'dyn.load(...)' BODY N --robigo robigo-rt --no-r`;
GNU R the same loop by hand, `R_DEFAULT_PACKAGES=NULL`, default JIT):

| body | robigo-rt | GNU R 4.6.2 | ratio |
|---|---:|---:|---:|
| `.Call("noop3", 1L, 2L, 3L)`, N = 20,000, before the lookup cache | 3,264 | 3,789 | 0.86 |
| the same, with the cache | **2,224** | 3,789 | **0.59** |
| per `PROTECT` + `UNPROTECT` pair (100 per call, N = 2,000) | 26.6 | 24.8 | 1.07 |
| per `INTEGER(x)[0]` | 19.6 | 29.1 | 0.67 |
| per `allocVector(INTSXP, 1)` | 373 | 81 | 4.6 |
| per `ScalarInteger(i)` | 364 | 117 | 3.1 |
| per `eval(symbol)` | 487 | 195 | 2.5 |

Experiment A's reference, 7,511 for the old runtime with its stub removed,
is now 2,224. GNU R on Linux resolves a `.Call` name with `dlsym` every
time (`CACHE_DLL_SYM` is Windows-only); robigo caches the result per
isolate by name and `PACKAGE`, cleared whenever the table changes, so the
routine found is the same (−1,040 per call). Where the allocating
crossings go (`alloc100`, self cost per allocation): about 110 in full
collections (every robigo collection is full and marks all of base; GNU
R's minor collections are cheap: the generational question, M8), about 70
in the heap's allocation, about 90 in the entry (stub, segment, scope,
safepoint, build). §13 makes these M-final bars; not gated in M1.

### Open questions for the foreman

- **The protect stack's depth at a `.Call`.** GNU R's `R_PPStack` holds
  its evaluator's own protections below a `.Call` (8 for a top-level
  `print(.Call(...))` in the corpus's recording), so a routine that
  unprotects one more object than it protected gets "Warning: stack
  imbalance in '.Call', 8 then 7" and continues. robigo's protect stack
  holds only C's protections, so the same routine gets "unprotect(): only
  6 protected items" (the capi corpus's `extptr.c` does this: `UNPROTECT(7)`
  after six protections). Matching it needs GNU R's depth at every call
  site, a logical account of its evaluator's protections like L7's for
  `gc()`. The rt variant of `extptr` balances its protections; the
  imbalance warning itself is GNU R's with robigo's depths.
- **The stub copies 59 stack-argument slots for any `.Call`** (about 60 of
  the 2,224); GNU R passes exactly `nargs`. An arity-aware stub goes with
  the narrowing and zeroing measurement in the follow-up.
