## 2026-11-14: D5 decision: no frame recycling (`none`), by the bar

- Bar: docs/ledger/g3.md, "M1 decision bars", D5. `recycle` is adopted if
  (a) its geomean instructions over PLAIN are at least 2% below `none`'s,
  or `none` allocates per call on a PLAIN row where `recycle` allocates
  nothing, and (b) the quarantine mode is clean on the rt slice, and (c)
  `binarytrees` is not slower than `none` beyond the tie band. Otherwise
  `none`.
- Runs: `2026-11-14-d5-runs.md` (`g3/x2-d5-recycle` at `c77bcb85`, at D2's
  decided `inline`) against `2026-11-14-x-base-runs.md` (base `e2207b4d`).
- Result:
  - (a) fails. Over PLAIN, recycle ÷ none = 1.0028: recycling costs 0.28%
    more instructions (its checks and the frame's rewrite, 151 per call
    on `plain`, against the 124 an allocation costs). The allocation
    clause does not apply either: `recycle` still allocates on every
    PLAIN row (the boxed argument and result values: `plain` 2 REALSXP,
    `named` 1), so there is no row where it allocates nothing.
  - (b) holds: both quarantine steps of the rt slice pass.
  - (c) holds: `binarytrees` 1.0014 in instructions, inside the tie band.
- **Verdict: `none`.** Nothing merges.
- For P1 (judgement, from the runs): the allocation clause is the one that
  can change. Once the VM passes unboxed values through calls (forced
  arguments and return values, C1's tagged promises), `none` still
  allocates a frame per call, and `recycle` would allocate nothing on
  `plain`, `defaults` and `named`, whose only other allocations are those
  boxed values. `env-fn` would not get there: it also allocates a STRSXP
  per iteration. One such row is enough for clause
  (a), and §13's "zero allocations per call" needs exactly that.
  Recycling also lowers estimated cycles already (−2.8% geomean over
  PLAIN). So `g3/x2-d5-recycle` is kept, not deleted, for a re-run of
  this bar after that P1 step; it is deleted once that run is recorded.
