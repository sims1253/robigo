## 2026-11-15: S1 follow-up, the S3 memos keyed by symbol id and set-associative (`robigo-rt`)

- What: V2b (#670, ledger `2026-11-14-v2b-cmp.md`) found the s3 calls
  row +13.7% on its branch, mostly S1's memo of `R_LookupMethod`'s
  searches (`dispatch.rs`) colliding: 64 slots, direct mapped by the
  method symbol's address. In the row, `area.sq`, `$.sq` and `$.default`
  are looked up every iteration; when two land in one slot, each lookup
  evicts the other's entry and every search runs in full. Which symbols
  collide depends on where the heap put them, so the cost came and went
  with allocation order (V2b: reordering the row's setup brought it back).
- Change: both S3 memos (the method lookup, and `installS3Signature`'s
  `generic.class` symbols) are one `Assoc` store: sets of 4 ways, the set
  picked by a key that is not an address (g3.md §5.3), the least recently
  used entry of a full set replaced. The method lookup's key is the
  method's `SymId`, spread by Fibonacci hashing so dense ids fill every
  set; the signature's is its FNV-1a hash. An entry still matches on
  (method, top environment, defining environment), and its validation by
  version boxes (§9.3) is unchanged: the same entry fields, the same
  checks in `memo_get`.
- Symbols and GC_MOVE: symbols are immortal (`IMMORTAL`), and the debug
  moving collector moves no immortal object (`gc/mover.rs`, `may_move`),
  so the old address key was stable; it is gone because §5.3's rule
  stands and because an address-derived index is what made collisions
  depend on allocation.
- Measurements (WSL2 workstation, Ryzen 9 5900X, 24 threads, rustc
  1.100.0; release `robigo-rt` from the private target
  `~/.cache/cargo-target-s1memo`; instructions per iteration by
  `scripts/idiom-vs-r.py`, the s3 row of `benchmarks/rt/calls-rows.toml`
  as written, and with its setup's first and last lines swapped):

  | build | s3 | s3, setup swapped | plain |
  |---|---:|---:|---:|
  | main `af7a7f19` (V2b merged) | 36,802 | 33,019 | 6,895 |
  | main `af7a7f19` + this change | 33,350 | 33,137 | 6,895 |
  | main `e2207b4d` (before V2b) | 32,371 | 32,372 | 6,908 |
  | main `e2207b4d` + this change | 32,452 | 32,462 | 6,908 |
  | V2b's branch `b4d021e6` | 36,795 | 33,020 | 6,895 |
  | V2b's branch + this change | 33,214 | 33,130 | 6,895 |

  On main the change takes the row from 36,802 to 33,350 (-9.4%), within
  0.6% of the swapped order, which never collided (V2b's branch: within
  0.3%). The two orders still differ a little; the likely cause, not
  measured, is the global environment's hash chains, which the setup's
  order of bindings changes and the memo does not touch. Where it did not
  collide, the change costs about 80 instructions per iteration (+0.25%):
  the set's scan and the use clock, over the row's three method lookups
  and three signatures. What V2b still adds to the row over `e2207b4d`
  is its ledger's 2%: `DOLLAR` duplicates the call before dispatching.
- Proof: `dispatch.rs`'s unit tests of the store (a set keeps 4 entries
  of colliding keys; a full set replaces its least recently used; an
  entry of the same key is replaced in place; 64 consecutive ids spread
  over 64 sets with no set over 4); `tests/rt/s3/*` (with `method-memo`,
  the memo's invalidations) and `tests/s3.rs` (both profiles, the active
  binding a memo must not keep); `scripts/rt-ci.py`, all six steps.
