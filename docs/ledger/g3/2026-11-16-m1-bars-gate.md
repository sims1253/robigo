## 2026-11-16: the M1 bars as a CI gate: perf-rt, perf's gate for robigo-rt

The M1 exit evidence (`2026-11-16-m1-exit-evidence.md`) found E1, E2, E7
and every peak-RSS bar measured by hand only: a regression of robigo-rt
would fail no pull request. This adds the gate, at the foreman's request:
- instructions only, since wall time on shared runners is noise;
- GNU R's numbers committed and versioned with the oracle pin, so CI never
  runs GNU R;
- at most about 5 minutes on an rt-mode PR's critical path, beside `rt`;
- an extension of `perf`'s gate, not a second one.

### The design

- **The bars, in one file:** `benchmarks/rt/m1-bars.toml`.
  - GNU R 4.6.2's instructions and peak RSS, from the oracle image
    (`2026-11-16-bars-oracle-baseline.md`), with the version they were
    measured for.
  - Today's robigo's numbers (G1, `../g3.md`, "M1 baselines").
  - One `[[bar]]` per row: `against` a reference, at most `max` times it.
    `met = false` marks a bar not met yet: s3 and fib, and e7-paste, the
    regression the lead accepted.
  - One `[[rss]]` per program.
- **The gate:** `scripts/perf.py rt-bars` is a subcommand of perf's own
  script, sharing its threshold (`THRESHOLD`, 0.5%, now one constant for
  `compare`, `recheck` and `rt-bars`). It runs three steps:
  1. **Measure:** the rows exactly as the bars tool does
     (`scripts/idiom-vs-r.py --rows benchmarks/rt/calls-rows.toml`, N
     against 2N under callgrind), in parallel groups with the long rows
     first, then peak RSS with `scripts/rss.py --runs 3`.
  2. **Bars:** a met bar that breaks fails. An unmet one never fails on
     its bar, and the gate says when it becomes met, so that it can be
     marked met.
  3. **Against main:**
     - a row more than 0.5% slower than main's run of the merge's base is
       measured again on this runner, with main's binary and this one;
     - it fails only if it is still more than 0.5% slower there;
     - peak RSS works the same way at 2%, because `ru_maxrss` moves by a
       few pages from run to run.

     This is perf's model: main's numbers (`perf-baseline.py`), then a
     paired check of what looks slower (`perf-paired.py`), because the
     runner a PR gets need not be main's.
- **The pin:** the gate refuses to run when the numbers' `version` is not
  the rt pin of `scripts/oracle-versions`. A pin moves only with GNU R
  re-measured in the new oracle image.
- **The job:** `perf-rt` in `.github/workflows/ci.yml`.
  - **When:** it needs only `select` and runs whenever `rt` does, in
    parallel with it.
  - **Build:** it restores rt's cargo cache (it does not save it, so the
    two jobs do not race on one key) and builds `robigo-rtapi` in release.
  - **Baseline:** on a PR, `perf-baseline.py`, which now takes the
    artifact's name, fetches main's `rt-bars-main` and `robigo-rt`
    artifacts. It waits up to 15 minutes for main's run of the base, and
    otherwise falls back to the nearest ancestor, as `perf` does.
  - **Gate and publish:** it runs `rt-bars`. On main it publishes both
    artifacts as the next baseline.
  - **Check:** `Check` needs it. `scripts/ci-check.py` allows its skip only
    when `rt` is skipped.

**Why a sibling job, not a leg of `perf`'s:** `perf` needs the old
runtime's `build` and runs in its image without Rust; it is skipped on
rt-mode PRs. A leg inside it would put every one of `perf`'s steps under a
leg condition, and would make robigo-rt's measurement wait for `build` on
full runs. So the gate's code is perf's, and so are its threshold, its
baseline machinery and its place in `Check`. Only the job is separate,
because its trigger, image and inputs differ.

### Cost

- **Locally:** the whole gate takes 16 seconds with 4 parallel jobs, on
  this machine (AMD Ryzen 9 5900X).
- **In CI, by the same build's cost:** `rt`'s release build takes 5 min 37
  s on its cache (#716's run). `rt` is the critical path of an rt-mode PR,
  at 12.5 minutes. With the build and a minute or two of callgrind,
  `perf-rt` finishes before `rt`, so it adds nothing to the critical path
  unless it waits for main's baseline. The PR's own CI run gives the
  measured time.

### Proof

- **Unit tests:** `scripts/test-perf-rt-bars.py`, 11 tests, run in the
  job:
  - a broken met bar fails, and an unmet bar only reports;
  - an unmet row's slowdown fails when the paired run confirms it;
  - a slowdown the paired run does not reproduce passes;
  - without main's binary, a slowdown fails as measured;
  - peak RSS has its own threshold;
  - numbers for another pin refuse to gate, and the committed file names
    real rows.

  `scripts/test-ci-check.py` covers `perf-rt`'s skip rule, and actionlint
  reports nothing new in `ci.yml`.
- **Deliberate regressions:** this branch's binary as main, against two
  binaries that add a loop to `ops::arith2` (every scalar arithmetic in
  the VM and the inliner):
  - **4 iterations:** `plain` +0.75%, `defaults` +0.72%, `named` +0.77% and
    `fib` +0.95% fail against main, each confirmed by measuring both
    binaries again. `env-fn` (+0.39%) and `superassign` (+0.20%) stay under
    the threshold, and no bar breaks. Exit 1.
  - **150 iterations:** 13 failures. Five met bars break: `plain` 0.889x,
    `defaults` 0.712x, `named` 0.903x, `env-fn` 1.065x and `binarytrees`
    1.121x. Every slowed row fails against main, including the unmet `s3`
    (+7.51%) and `fib` (+124%), which fail only on the regression. Exit 1.
  - The unregressed binary passes, exit 0.
- **In CI:** the pull request's own run. Main has no `rt-bars-main` yet, so
  it gates the bars only. A throwaway draft PR on top of it, with the
  150-iteration regression and nothing else, shows the job failing in CI.
- **Limit:** the against-main path runs in CI only after main has
  published its first `rt-bars-main`.

### Not covered

- **Estimated cycles:** E2 also asks for them; the gate holds
  instructions only, as the foreman asked.
- **Wall time:** E1's wall-time bar is wall time, so it stays a hand run.
- **The CPU:** GitHub's runners vary, while the committed GNU R numbers
  come from this machine's CPU. The bars' margins are wide: the
  narrowest met bar today is binarytrees at 0.925x. A bar can therefore
  move by a few tenths of a percent with the runner, and the paired check
  absorbs that against main.
