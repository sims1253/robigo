## 2026-11-16: P1 step 11, E2 `fib` fix 3: two unboxed doubles go straight to the kernels' double arms

Fix 3 of `fib`'s three (`2026-11-16-p1-gaps.md`): "keep typed scalars
through the run, without `vm::num`'s re-dispatch per operand". Step 6's
conditions apply (`2026-11-16-p1-inline.md`).

- Base: `g3/p1-fib-argshape` at `f15d6612` (#708; its code is the
  `3bde32ef` its entry measured). Change: branch `g3/p1-fib-typed`,
  measured at `bb0f474c` (`robigo-rt`).
- Where the instructions went. A function profile of `fib(18)` on the
  base put about 1,105 instructions per call in `inline::enter` itself
  (the body loop and fused steps are inlined into it), 493 in forcing
  arguments, 62 in reads and 43 in `ops::relop2`. In those, every
  arithmetic and comparison converted each operand with `vm::num` (a match
  on the slot's tag, then the object case), then matched the pair in
  `ops::arith2` or `ops::relop2`; `relop2` is not inlined, so each
  comparison was a call.
- What changes (`crates/robigo-rt/src/inline.rs`):
  - **Two doubles directly.** `arith_slots` and `relop_slots` take two
    registers. Two unboxed doubles go to the kernel's double arm:
    `ops::arith2` with both operands known to be doubles, which the
    compiler folds, and `relop::real`, `relop2`'s arm. Any other pair takes
    `vm::num` and the general match as before, inline. The fused compare
    and arithmetic steps, the argument shapes, the body loop's `Arith` and
    `Relop`, and `pure` use them.
  - **Mixed operands cost what they did.** The general path stays inline
    at each site. A first version called it out of line, which cost the
    rows whose operands mix integers and doubles up to 0.9%. Folded arms
    for a double and an integer were measured too: `fib` +0.55% against
    this version, the others within 0.2%, so they are not kept.
  - **The same semantics.** The kernels are the same functions, so which
    of NA and NaN an operation keeps, the sign of zero and infinities are
    what they were. Two doubles never overflow, so no give-up is lost.
  - **The table's bound (the #708 review thread).** `program` took a
    table after dividing its length by the step size. It now takes one
    bound, its instruction bytes and one step. A const assert
    (`MIN_TABLE`) pins that an argument shape is shorter than any table,
    which both readers' length checks rely on, so a change of either
    size fails to compile instead of letting one be read as the other.
- Attribution on `fib(18)` (`vm::run` inclusive, callgrind), measured on
  the first version: the doubles' path alone is 6.8%, the bound another
  0.8%.

Found on the way (Sol's review, then checked against GNU R 4.6.2; both
also with inlining off, in paths this step does not change):
- In compiled code, robigo-rt keeps the other of NA and NaN for a double
  and an integer under `+` and `*`. `g <- function(a, b) a + b`, run in a
  loop, gives NA for `g(NaN, NA_integer_)` where GNU R gives NaN, and NaN
  for the reverse where GNU R gives NA. At top level the two agree. The
  VM's arm for a double and an integer (`ops::arith2`'s, which the
  inliner's general path shares) is the one to port again from
  `bcEval`'s arithmetic.
- `1e308 %% 1` and `(-Inf)^1e308` give GNU R's values without its
  warning "probable complete loss of accuracy in modulus" (`myfmod`,
  which `R_pow` calls for a negative base).
