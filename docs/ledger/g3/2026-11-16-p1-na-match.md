## 2026-11-16: `NA_character_` never equals the string `"NA"` in `Seql`

Found by the D10 audit of the string comparisons (X4): robigo-rt's
`identical::seql` compared bytes after the pointer test, so `NA_STRING`
and a string `"NA"`, the same bytes and both native, were equal. GNU R's
`NA_STRING` is a cached CHARSXP, so `Seql`'s pretest (`IS_CACHED(a) &&
IS_CACHED(b) && ENC_KNOWN(a) == ENC_KNOWN(b)`, memory.c:5014) tells them
apart by pointer. Most callers test for NA first; `match5`'s scalar case
(`unique.rs`, `scalar_match`) did not.

| | GNU R 4.6.2 | robigo-rt, main `d25d0586` |
|---|---|---|
| `match(NA_character_, "NA")` | NA | 1 |
| `match("NA", NA_character_)` | NA | 1 |
| `NA_character_ %in% c("NA", "b")` | FALSE | TRUE |
| `match(c(NA_character_, "a"), c("NA", "a"))` (the hashed case) | NA 2 | NA 2 |

- Base: main at `d25d0586`. Change: branch `g3/p1-na-match`, measured at
  `f2ced105` (`robigo-rtbuiltins`).
- **The fix:** `seql` is true for the same CHARSXP, false when either is
  `NA_STRING`, else the byte and encoding comparison as before. Every
  other CHARSXP robigo-rt makes is interned, so this is `Seql` for every
  pair.
- `tests/rt/unique/match-na-string.R`, recorded on GNU R 4.6.2: the
  scalar and the hashed cases of `match` and `%in%` both ways, and
  `identical`. The base subset needs no change (`scripts/base-subset.sh
  --check`).
- Admission at `f2ced105`: `scripts/test-rt-ci.py` and `scripts/rt-ci.py`
  pass every step (conformance 309/315, and 308/314 or 305/310 in the
  modes whose `.requires` leave cases out; the failures are main's
  unratcheted ones). `scripts/lint.sh` and `cargo fmt --check` pass.
  `robigo-rtcore` and `robigo-heap` are unchanged, so no Miri run.
- Commands: `scripts/rt-bars.sh` twice for each binary, `s3` three more
  times, `scripts/rt-bars-compare.py --a main ... --b na ...`; the E7 rows
  with `scripts/idiom-vs-r.py --rows benchmarks/rt/calls-rows.toml
  --filter '^e7-' --no-r`.
- Raw JSON: `data/2026-11-16-p1namatch-f2ced105/run{1,2}-*.json`,
  `run{3,4,5}-s3.json` and `e7.json`, with the base's as `base-run*` and

Found on the way (Sol's review, on main too, unrelated to byte equality):
robigo-rt's base subset does not bind `levels<-.factor`
(`crates/robigo-rt/proto/base-bound.txt`), so a factor's level
replacement falls through to the primitive. For levels `c(NA, "NA")`
replaced by `c("NA", NA)`, GNU R 4.6.2 gives levels `"NA"` and codes
`1 NA`; robigo-rt gives levels `"NA", NA` and codes `1 2`.

Review: Sol approved `f2ced105` with no findings.
- It ran the `tests/rt/unique`, `strings`, `subset` and `sort` areas (5/5,
  1/1, 8/8, 14/14) and GNU R 4.6.2 probes of scalar and hashed `match`,
  `incomparables`, `%in%`, `unique`, `duplicated` (through its
  `.Internal`), `identical`, the relational operators and subscripting by
  name.
- It checked every caller of `seql` against GNU R's counterpart (`match5`
  and `Seql`, `sequal`, `identical`'s string and CHARSXP comparisons, tag
  names) and found the early return changes only `NA_STRING` against the
  string `"NA"`.
- Where GNU R itself matches NA to `"NA"` by bytes (`pmatch`, `charmatch`,
  `switch`, `$`, `[[<-`), robigo-rt's byte comparisons keep that.
