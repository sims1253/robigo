## 2026-11-16: P1 step 5, unboxed values through calls: a closure's scalar goes to its compiled caller's register unboxed

The fifth P1 family (base and bars: `2026-11-15-p1-base.md`; steps 1-4:
`2026-11-15-p1-frames.md`, `2026-11-16-p1-forced.md`,
`2026-11-16-p1-call.md`, `2026-11-16-p1-lookup.md`). This is the work
list's "unboxed values through calls". Before it, a closure whose body
ended in arithmetic boxed the result, one REALSXP per call, for a caller
whose register would have taken the scalar unboxed.

- Base: main at `6ca61fea` (#688 and #689 merged). Change: branch
  `g3/p1-unboxed`, measured at `2fe67bb4` (`robigo-rt`, `robigo-rtcore`).
  The head `a0d0d057` differs only in how `run_function` returns the flag
  and in a test. On `fib`, `plain`, `s3` and `superassign` it measured the
  same instructions per iteration (`callgrind-diff.py`, one run each).
- What changes:
  - **The callee's `Ret` and `Return`.** When compiled code calls a
    closure, the callee's `Ret` or `Return` may write an unboxed double,
    integer or logical, as its arithmetic left it, straight into the
    caller's register. `args::apply` permits it (`Act::unboxed`) when a
    caller activation made the call. `vm::exec` reports that it did
    (`Act::left_unboxed`, set only on that branch).
  - **The function context.** `run_function` boxes such a value only when
    the record has on.exit code, which may read it as `returnValue()`. Else
    the slot keeps it, and the record's returnValue stays unset (nothing
    else reads it). `function_context_raw`'s body returns the flag.
    `function_context`, whose bodies return objects (dispatch, `eval`),
    passes a constant false that inlining drops.
  - **The caller's cleanup.** `args::apply` gives `cleanup_envir` no value
    for an unboxed result, and skips the getter call's duplicate. An
    unboxed scalar is no object: the frame cannot hold it, and nothing else
    references it.
  - Builtins, the apply hook, dispatch and `eval`, whose callers take
    objects, still get boxes.
- A first version asked the out slot instead of the VM. Both
  `args::apply` and `run_function` read the slot and tested its tag on
  every call, including calls that cannot leave a scalar (dispatch's).
  `s3` paid 83 instructions per iteration (32,154 to 32,237). With the
  flag from the VM it is 32,141.
- Admission at `a0d0d057`: `scripts/test-rt-ci.py` and `scripts/rt-ci.py`

Allocations per iteration fall where a closure's value was a scalar:
`plain`, `defaults`, `named` and `env-fn` lose one REALSXP each. `fib`
drops from 20,917 to 16,737 objects per call of `fib(18)` (REALSXP from
12,556 to 8,376), `binarytrees` from 2,809 to 2,554. `superassign` and
`s3` are unchanged: their closures return objects.

`superassign` costs 41 instructions more per iteration
(`callgrind-diff.py` by function: `vm::run` +14, `function_context_raw`
+12, `args::apply` +11, `vm::exec` +4). Its callee returns `invisible(bal)`,
an object, so nothing is unboxed; this is the flag's plumbing on such a
call. Reading the flag from `with_record`'s value, not a captured
variable, did not change it.

0.6x), `fib` 4.07x today's robigo (bar 1.0x).
