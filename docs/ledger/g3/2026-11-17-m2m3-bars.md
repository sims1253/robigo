## 2026-11-17: M2/M3 decision bars: D8, D13, D2u, D11, D12, D0, E2f

Written before any variant is built past a compile check. The foreman
signs them off in the pull request that adds this entry. As in M1, a bar
is fixed once a run cites it. A change is a new dated entry that names the
bar it replaces and why, and it is committed before the runs it governs
(§15.2). These bars finalize the M2/M3 plan's §C with the lead's decisions
(F3 A: the instruction gate stays, cycles are reported; F4 A: D0's count)
and with G2's rows. D10's bar is X/P1's, with its own rows
(`2026-11-17-d10-bar.md`).

### Protocol

M1's protocol holds (`../g3.md`, "M1 decision bars", "Protocol"): the
binary, admission through the rt slice, instructions and estimated cycles
N against 2N, allocations from `ROBIGO_GC_STATS=1`, peak RSS from
`scripts/rss.py --runs 5`, the geomean, two runs of every table, one
machine per instruction comparison, the records, and a failed premise
going to the lead. These are the changes the M1 evidence earned (plan §C):

- **Both modes.** Every rule must hold with pure-closure inlining on (the
  default) and with `ROBIGO_NO_INLINE=1`. A variant that wins in one mode
  and loses in the other loses.
- **Wall time decides D8, D13 and D12,** with peak RSS. Instructions guard
  them: a row worse than a bar's instruction limit loses whatever the wall
  time says. Wall time follows §13:
  - the release build (`cargo build --release --locked -p robigo-rt`);
  - each program batched to at least 0.05 s;
  - 11 interleaved rounds of every variant, and the medians compared;
  - on the desktop (AMD Ryzen 9 5900X) and on m0pad (AMD Ryzen 5 PRO
    5650U), with A3's harness, which moves the cycles study's `wall13.py`
    into `scripts/`. A wall bar holds only if it holds on both machines.
- **Estimated cycles** under the pinned model (`--I1=32768,8,64
  --D1=32768,8,64 --LL=33554432,16,64`, `scripts/perf.py`'s
  `PINNED_CACHE`) are reported on every run and decide nothing.
- **The tie band** is ±1% instructions or ±2% wall time. Inside it, the
  variant named first wins.
- **GNU R is not a reference in these bars.** Each compares robigo-rt
  variants, so the choice of GNU R rival (F2, A0's entry
  `2026-11-16-a0-oracle-gap.md`) changes none of them.

### D8: the vector header (X3)

- **Question:** a 24-byte vector header with §8's storage for what
  `TRUELENGTH` holds, or today's 32 bytes?
- **Variants:** `h32` (today), `h24` (X3's branch). Both keep `TRUELENGTH`'s
  storage and the shared-CHARSXP branch in `TRUELENGTH`/`SET_TRUELENGTH`
  (g3.md §8). A variant without them is a control.
- **Workloads:** LAYOUT's `scalars`, MEM, CALLS, SUITE and E7.
- **Rule:** `h24` wins only if all of these hold:
  - `scalars.R`'s peak RSS is at least 10% lower;
  - no MEM program's peak RSS is more than 1% higher;
  - the wall geomean over MEM and SUITE's programs is better beyond the
    tie on both machines;
  - no row of the workloads is more than 1% worse in instructions;
  - the rt slice and the conformance suite give identical results.
- **Decided:** wave 1, as the row choice of D13's 2×2.

### D13: node sizes (X3)

- **Question:** per-type node sizes (a 40-byte LISTSXP), or today's
  uniform 48 bytes?
- **Variants:** `n48` (today), `nT` (X3's branch).
- **Workloads:** LAYOUT's `plist` and `henv`, and `binarytrees`.
- **Rule:** `nT` wins only if all of these hold:
  - peak RSS is at least 5% lower on `plist.R` and on `henv.R`;
  - collection time per MB allocated is at most 3% worse;
  - the wall rule of D8.
- **The 2×2:** X3 builds {`h32`, `h24`} × {`n48`, `nT`}. D8's rule, applied
  at `n48`, picks the header, and D13's rule then decides on that row.
- **Collection time is not measurable yet.** `ROBIGO_GC_STATS` reports
  collections, overshoot and allocations, not time. X3 adds a line for the
  time spent in collections to the report before its runs. A run without
  it is preliminary and decides nothing.
- **Decided:** wave 1.

### D2u: unhashed non-call environments

- **Question:** GNU R's representation (a `FRAME` pairlist without a
  `HASHTAB`), or today's slot frames?
- **Variants:** `gnur-frame` and `slots` (today). GNU R's form is named
  first, so it takes ties: it is simpler and ordered by construction.
- **Workloads:**
  - ENVS;
  - the listing-order cases: `ls()`, `as.list()`, `mget()` and
    `eapply()` on environments made by `new.env(hash = FALSE)`,
    `list2env()` and `eval(, list)`. They are recorded on GNU R 4.6.2 and
    ratcheted before D2u's runs.
- **Rule:** `slots` stays only if all of these hold:
  - the geomean instructions over ENVS are at least 5% lower;
  - no ENVS row is more than 1% worse;
  - bytes allocated per iteration are not higher on any ENVS row;
  - the listing-order cases pass.
- **Decided:** wave 3.

### D11: the run-once engine

- **Question:** one engine with the `Eval` profile (today), or an exact
  minimal `eval` for first evaluations outside loops?
- **Variants:** `one-engine` (today), `mini-eval` (a branch built from V1's
  code).
- **Workloads:**
  - COLD, as rows and as programs;
  - stage 0's build wall time and the rt suite's wall time, reported;
  - CALLS.
- **Rule:** `mini-eval` wins only if all of these hold:
  - `startup`, `runonce` and `source5k` each take at least 15% fewer
    instructions;
  - their wall time wins beyond the tie on both machines;
  - no CALLS row is more than 0.5% worse;
  - `ROBIGO_REF_EVAL` runs clean on the variant.
- **Decided:** wave 5. `startup` exists only once L5 lands, so a run
  before it is preliminary.

### D12: growth reallocation

- **Question:** copy, as `EnlargeVector` is written, or remap the pages of
  a large unshared chunk (above 64,464 bytes) with `mremap`?
- **Variants:** `copy` (today), `mremap`.
- **Workloads:** GROWTH (`cappend.R` is the control: a new vector each
  time, which remapping cannot help), `churn.R`, CALLS and SUITE.
- **Rule:** `mremap` wins only if all of these hold:
  - `growdbl.R` and `listgrow.R` are at least 10% faster in wall time on
    both machines;
  - no GROWTH or MEM program's peak RSS is higher;
  - no other row or program is worse beyond the tie;
  - the address relations are GNU R's: growth keeps the same object
    exactly when GNU R keeps it, so an address that GNU R keeps is kept,
    and one that GNU R changes changes.
- **Decided:** wave 4.

### D0: the C crutch (D0c, then D0p)

- **The count (F4 A).** D0c counts the distinct builtins the three boot
  paths reach (the plan's D0c method) on GNU R 4.6.2. From that count it
  subtracts what is Rust at M3:
  - the evaluator-owned and designed-away builtins of g3.md §10 (eval.c,
    envir.c, errors.c, context.c, debug.c, memory.c, objects.c, match.c,
    main.c);
  - the builtins robigo-rt's registry implements in Rust at D0c's base
    SHA (M1's 188 rows).
- **Rule:** §10 as written. `robigo-cbase` is adopted only if both hold:
  - the count is at least 150;
  - D0p's adapter costs at most 1.10x the Rust port's instructions per
    call on each of attrib.c (`d0-attr`, `d0-attributes`, `d0-names`),
    bind.c (`d0-unlist`, `d0-cbind`, `d0-rbind`) and paste.c (`d0-paste`,
    `d0-paste0`). A file's cost is its rows' geomean.

  Otherwise the boot set is ported. A count below 150 decides "port" and
  skips D0p, because the rule is a conjunction.
- **Decided:** the count in wave 0, the pilot (if any) in wave 1.

### E2f: fib's eager leaves (X6)

- **Question:** keep lazy argument evaluation (today), or evaluate leaf
  arguments early under the guards of the plan's §E.c?
- **Variants:** `lazy` (today), `eager-leaves`. First, the inexact control
  `g3/x6-fib-eager-control` sets the bound: if it cannot reach 1.0x
  today's robigo on fib, E2f is declined, and G8 keeps fib's bar.
- **Workloads:** `fib`, CALLS, and X6's observer suite:
  - warning order;
  - finalizers by eval count;
  - "evaluation nested too deeply";
  - `sys.call` while a promise is forced;
  - active bindings;
  - interrupts.
- **Rule:** `eager-leaves` wins only if all of these hold:
  - `fib` is at or below 1.0x today's robigo in instructions and in
    estimated cycles;
  - no CALLS row is more than 0.5% worse;
  - the observer suite is identical against the oracle and under
    `ROBIGO_REF_EVAL`.
- **Decided:** wave 4, once the evaluator stops moving.
