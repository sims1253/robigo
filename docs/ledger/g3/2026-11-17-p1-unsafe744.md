## 2026-11-17: #744's frame-API soundness gaps: the `<<-` memo deleted, `set_var_at` unsafe

Issue #744, from a read-only unsafe-code review of robigo-rtcore, assigned
to X/P1 by the foreman as a drive-by.

- **`SuperAssignCache`** (`env/slotapi.rs`) was a safe, `Copy`, untraced
  `<<-` memo. A hit matched each frame's shape by address alone and then
  stored into the remembered slot index, with no check against the frame's
  capacity or the slot's symbol. Kept across a collection, it could index
  past a smaller frame allocated at a reused address. Nothing outside
  rtcore's own tests called it: the VM's `<<-` goes through `vm.rs`'s
  `set_var` and the inliner's write log. It is deleted, with
  `SUPER_ASSIGN_HOPS`, `Cx::set_var_super`, `super_hit` and `super_record`.
  When V1 builds the `<<-` cache of docs/g3.md §5.3, it should key on the
  symbol, check the index against `layout::capacity`, and be traced by its
  owner.
- **`Cx::set_var_at`** is now an `unsafe fn`. Its `SetVarTarget` is a raw
  location and frame, valid only while nothing collects and no binding is
  written. Its one caller, the inliner's `WriteLog::commit`, states why both
  hold: nothing collects while a run holds the log, a commit neither
  allocates nor collects, and the run binds no names.
- **The minting invariant** (lib.rs, "Minting"; `Ref::child`) said that an
  object's fields do not change during an `&'g Cx` interval. Several `&Cx`
  operations write fields:
  - dropping early argument values clears delayed slots (`note_effect`,
    `note_write`);
  - the code-source marks write header bits (`mark_code_source`,
    `note_code_write`);
  - `set_srcref` sets the context's srcref.

  The invariant is now what the code keeps: nothing collects or moves, and
  no payload that a view or slice borrows changes. An object that a cleared
  word held stays live until the next collection, which needs `&mut Cx`.
- **`recycle_frame`'s precondition** is now in its doc. The pool's
  reachability test counts heap edges and escapes, not roots, so a root
  still naming a recycled frame would see the next frame of that capacity.
  No memory is reused behind it: a root keeps the frame live through the
  collection that empties the pool.
- **The residue tables** (`env/promise.rs`) key on frame addresses, but
  each entry traces its frame as a precise root. The address cannot be
  reused while the entry exists, and a moving collection updates the word.
- **A known, bounded gap: item 4's helpers.** About 50 crate-private safe
  functions take a raw `Sexp` or `Rec` and do unsafe work on the caller's
  knowledge, for example `raw_ref` (`context.rs`), `mark_escaped` and
  `Rec`'s field getters. They are `pub(crate)` or private, so no code
  outside robigo-rtcore can call them. Their obligations are the crate's
  own, kept by its unsafe blocks' SAFETY comments rather than by the type
  system. They stay as they are, by the foreman's decision, and no issue
  tracks them. A helper that becomes `pub` must become an `unsafe fn` with
  a `# Safety` section first (AGENTS.md, rule 7).
- **Tests.** `super_assignment_memo_hits_and_misses` becomes
  `super_assignment_walks_slot_frames`. It covers the same chains (two of
  the same shapes, an overflow binding on the way, the global fallback)
  through `set_var`. `frame_op_cost`'s `super` op is `set_var` from the
  enclosure.

### Sol's review: an inline commit could collect (P1), fixed in `228155ef`, re-check approved

Sol found that the SAFETY argument above for `WriteLog::commit` was false.
`set_var_target_raw` accepted two kinds of argument slot:
- a generic's argument slot that a method's alias reads (`META_ALIASED`);
- an `ALIAS` slot.

A store into either goes through `set_binding_value → store_unshared →
ensure_object`. That allocates and may collect while the log still holds
the other logged targets and values as raw words. The code had behaved this
way before #744; #744 only wrote down the invariant the code did not keep.

- **The fix.** `set_var_target_raw` now refuses those slots, using the same
  test `set_binding_value` makes before `store_unshared`, and the inline run
  gives the write back to the real call. So `set_var_at` neither allocates
  on the R heap nor collects. Rust-side tables (the residues, the remembered
  set) may still grow, which never collects. Its doc, `set_var_target_raw`'s doc and the commit's SAFETY
  comment now say so, and why.
- **The test.** `tests/rt/s3/alias-superassign-loop.R`, recorded on GNU R
  4.6.2 and ratcheted, runs `<<-` from inlined loop bodies into a generic's
  aliased argument, next to a second logged write. It passes in the default
  mode, under gctorture, and under gctorture with `ROBIGO_GC_MOVE`. It could
  not be made to fail on the old code: in every probe, the first write into
  the aliased argument ran in the VM before the loop body was inlined, and
  that write ends the alias. The case guards the fix; it is not a witness.
- **Checks at `228155ef`.**
  - `cargo fmt --check`, `scripts/test-rt-ci.py`, `scripts/rt-ci.py` and
    `scripts/lint.sh` pass. Conformance is 311/317, and 310/316 or 307/312
    in the modes whose `.requires` leave cases out. The failures are main's
    unratcheted ones.
  - Miri on `robigo-rtcore`: 110 tests pass.
  - The binary was rebuilt in an empty `CARGO_TARGET_DIR` and has the same
    sha256 as the shared target's build:
    `6045ee07e65ebe1f5a63e8611670346cef425136e31b1c4fefff0724c0254655`.
- **The bars against the same main `66c1a0b1`.** The geomean is 1.0002 in
  instructions and 1.0003 in estimated cycles. Every row is 1.0000 except
