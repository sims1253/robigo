## 2026-11-17: V4 step 1: every opcode cmp.R emits translates

Package V4, step 1 of 5 (the foreman's order: opcodes, promise code per
promise, the install path, the JIT-cost harness, the crosscheck
follow-up). V4 crystallizes JIT-compiled closures through cmp.R, so any
closure can carry any opcode cmp.R emits, not only the ones base's code
uses (V3's census).

- **Tree:** branch `g3/v4-1-opcodes`, from main `aa3d100e` (V3, #778).
- **Oracle:** GNU R 4.6.2; its cmp.R and eval.c.

### What cmp.R 4.6.2 emits

Every opcode named in cmp.R's code outside comments (112), against the
translator's arms:

- **All translate but four.** `DOTSERR` was the one left that cmp.R
  emits: `cmpSym` emits it for `...` evaluated as a value. It now raises
  bcEval's `error("'...' used in an incorrect context")` against the
  context's call, then keeps the stack's shape with the value bcEval never
  pushes. `tests/rt/bctrans/dotserr.R` has four cases, recorded on 4.6.2.
- **`INCLNK`, `DECLNK`, `DECLNK_N`:** cmp.R emits them only where
  `checkNeedsInc` is true, and 4.6.2's always returns `FALSE`. They stay
  "not implemented yet" rather than a guess.
- **`LOG`, `LOGBASE`:** they wait on B5a's `log`.
- **Defined but never emitted** (old byte code, or code made by hand with
  `mkCode`): `PRINTVALUE`, `DUP`, `GETGLOBFUN`, `GETSYMFUN`,
  `STARTC`/`DFLTC` (commented out in cmp.R), `ISNUMERIC`. They raise "not
  implemented yet".

### The crosscheck

`DOTSERR`'s difference from the from-source code has its own expected
class, "`...` as a value": the port reads `...` and raises the same error
when it runs. The conformance crosscheck stays at 0 unexpected.
