## 2026-11-17: X9-1a, the C stack per R call: `vm::run` and `apply_with` keep less live across the callee

X9 (the foreman's package, 2026-11-17) covers the call path behind E1's M3
`trycatch` row. It also covers the C stack per R closure call, which this
entry is about.

On main, `g <- function(n) { d <<- n; g(n + 1) }` stops at depth 2,386 with
"C stack usage … too close to the limit". GNU R 4.6.2 reaches 4,988 and
stops there on `expressions` (5,000). That blocks
`tests/r/conditions/eval-depth-limit`, `tests/r/jit/native-closures` and
part of `tests/r/basics/nested-inline-calls`.

This entry covers steps (a) and (b) of the approved plan. Step (c), the
context-record stack, follows in its own PR.

### GNU R's C stack does not grow with R depth (measured)

GNU R 4.6.2 runs a byte-code closure called from byte code inside the same
`bcEval_loop` (`INLINE_CLOSURE_CALL_OK`, `START_BCFRAME_CALL`,
`setup_bcframe_call`, `DO_INLINE_CLOSURE_CALL_RETURN`, eval.c:7389–8100),
with the call's `RCNTXT` in a bcframe on the node stack. At the bottom of
`g(0, m)`, `Cstack_info()[["current"]]` is 18,400 bytes for every m from 20
to 3,000. A shallower first call reads more (22,416 at m = 10), which is the
JIT warming up. So "GNU R uses X KB per call" is a budget for robigo-rt to
meet, not a figure GNU R itself uses.

- **The budget.** `R_CStackLimit` is 0.95 × the rlimit, 7.97 MB of 8 MB.
  `eval-depth-limit` needs about 5,500 levels: the 5,000 of `expressions`,
  plus the 500 more a calling handler gets (`f(1000)` inside one). That is
  about 1.4 KB per level.
- **The faithful long-term design.** In-loop calls, with no Rust recursion
  per VM-to-VM call, would make the C stack independent of R depth, as in
  GNU R. That is a VM redesign, recorded here for the JIT tiers (M6) or a
  later VM package. It is not in X9.

### Where robigo-rt's stack went (measured on main)

gdb at the bottom of a fixed-depth recursion, frame sizes from `rsp`:

| frame | bytes per level | what it held |
|---|---:|---|
| `args::apply_with::<false>::{closure#0}` | 2,144 | the context record (`size_of::<Context>()` 528, with a 200-byte `jmp_buf`), the matching scratch (slot inits 224, formals' tags and defaults 192, the matcher's buffers), and the lazy `promargs` fill data, all live while the callee ran |
| `vm::run` | 1,024 | its largest arm: LLVM shares the arms' stack slots, so the frame is the size of the biggest one. `loop_region`, inlined, put a whole `CTXT_LOOP` record here |
| `vm::exec` | 160 | |

That totals 3,328 bytes per level, so 7,966,585 bytes at depth 2,386.

### (b) `vm::run`

- `loop_region`'s `CTXT_LOOP` record now sits in an `#[inline(never)]`
  `loop_context`. `run`'s frame goes from 968 to 520 bytes. `plain` and
  `defaults` cost +3 instructions each.
- Moving all of `loop_region` out of line instead cost `plain` and
  `defaults` +1.1%: about 19 instructions per call, spread over `run`'s
  dispatch loop (more `View` reloads and spills). This is H's trap.
- Moving `call_special_internal` out of line did not shrink the frame, so it
  stays inline.

### (a) `apply_with`

Everything the callee does not need runs in an `#[inline(never)]`
`prepare::<GENERIC>`, which returns before the body runs. That covers
argument matching (the plan hit or the matcher), the slot inits,
`new_closure_frame` and the early arguments. The closure that spans the
callee keeps only three things:
- the context record;
- `FillData`, which now owns the lazy `promargs` fill data (392 B, sized by
  the matcher's variant; the plan's variant needs 194);
- a small `CallState`: a generic's list and the early-end state.

The call's inputs move into the scope closure (`CallIn`), and `prepare`
reads them in place.

Variants tried, measured against main:

| change | result |
|---|---|
| a plain split: ten arguments, a `Prepared` struct returned through memory | `s3` 1.0080, `trycatch` 1.0065, `binarytrees` 1.0101 (+68 per call) |
| `early_args` inlined into `prepare` | `binarytrees` 1.0092 |
| inputs through one `&mut CallState`, `(code, newrho)` returned in registers | `binarytrees` 1.0055, `s3` 1.0057 |
| `early::value` / `early::run` forced inline | worse (+47 / +41) |
| the move closure: `CallIn` in the closure's environment, read in place | +8; `vm::run` itself −10 per call |
| `CallState` with only a generic's list; the matcher's formals pushed instead of `Matched` rebuilt | worst row 1.0017 (this PR) |

Capturing by reference had made `vm::run` store each value and also a
pointer to it, which is why the move closure helps.

### Step (c), the context-record stack (approved; its own PR)

The design was sent to the foreman and approved with five conditions.
Condition 1 is checked here:
- **GNU R 4.6.2.** Nothing relates a context record's address to the C
  stack. The `R_CStackStart` arithmetic compares only with locals (`&dummy`,
  `&ans`: errors.c:117/127, platform.c:3451, grep.c:398) and with fault and
  stack-check addresses (main.c:513/770/846). `cstacktop` is the top of the
  pointer-protection stack (context.c:172/255). Records are compared by
  chain equality, never ordered by address. GNU R 4.6.2 already keeps a
  byte-code call's `RCNTXT` off the C stack (`BCFRAME_CNTXT` on
  `R_BCNodeStack`, eval.c:7302/7393).
- **robigo.** `c_stack_usage` (limits.rs:218–223) uses a local. rtcore reads
  records through `addr_of!` only. rtapi's C makes no address comparisons of
  `R_GlobalContext`.
