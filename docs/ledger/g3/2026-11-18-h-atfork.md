## 2026-11-18: one set of fork handlers for the process's locks

- Why: two open findings.
  - #851's review: the symbol arena registered its `pthread_atfork`
    handlers lazily, inside its first lock (`Once::call_once`). A fork
    from one thread while another was inside that first `call_once` left
    the child's `Once` in progress for ever.
  - H's note on #842: B's `LIVE_ISOLATES` count and clib's `ENV` lock had
    no fork handlers at all. A child forked while another thread held one
    blocked on its first isolate start or end, or its first `Sys.setenv`.
- What:
  - `robigo-heap/src/fork.rs`: one `pthread_atfork` triple for the
    process.
    - It is registered before `main` by an `.init_array` constructor,
      while the process has one thread, so no fork can race the
      registration. `Core::new` calls the same registration in case a
      linker dropped the constructor. The registration is an atomic swap,
      not a `Once`, so a child never inherits an initialization in
      progress (Sol r1 S1).
    - `prepare` first takes `FORK`, a pthread mutex of its own that
      serializes whole forks, so two forks' handlers never interleave
      (S3). It then takes the embedder's locks, given by `set_fork_locks`
      (robigo-rtcore: `LIVE_ISOLATES`, then `ENV` exclusive), and last the
      arena's.
    - `parent` and `child` release in the reverse order, only what that
      `prepare` took.
    - The module's doc holds the process's lock order, the one place it is
      written: `FORK`, `LIVE_ISOLATES`, `ENV`, the arena. It also says what
      `prepare` waits for, and why std's environment lock is not in the
      order.
  - **std's environment lock (S2).** `EnvWriter::set`/`unset`
    (`clib.rs`) call the C library's `setenv`/`unsetenv` under `ENV`
    exclusive instead of `std::env::set_var`.
    - So robigo never takes std's lock for writing. A child forked while a
      std reader (`std::env::var`: 67 sites in the rt crates, and
      `vars_os` in `Sys.getenv`) held it shared inherits a reader count
      that blocks only writers, and the child's `Sys.setenv` still writes.
    - The inversion with `std::process::Command`'s fork fallback, which
      holds std's lock shared across `fork`, is gone: no robigo thread
      waits on std's lock while it holds `LIVE_ISOLATES` and `ENV`.
      robigo-rt does not spawn through `Command`.
    - std's readers now run concurrently with the writer. They read
      through glibc's `getenv`, which glibc 2.41 (`MIN_GLIBC`) makes safe
      against `setenv`; on an older glibc only one isolate may write, as
      before.
  - `arena.rs` loses its lazy registration and keeps `lock_for_fork` and
    `unlock_after_fork` for the triple. Its test guard
    (`hold_lock_for_test`) is an `unsafe fn` whose guard is neither `Send`
    nor `Sync` (S5).
  - `isolate.rs`: `fork_take` and `fork_release` hold the two guards in a
    static between the handlers. `FORK` guarantees one fork at a time.
  - `clib.rs`: `env_write_lock`, for the handlers. B's latest push made
    `env_locale` and `c_locale` take `ENV` shared, so `prepare` must take
    it exclusive, and does.
  - `docs/g3.md`: a note under L6. `ENV` and `LIVE_ISOLATES` are
    process-global by necessity (one environment per process), hold no R
    state, and are ordered in `fork.rs`.
  - Two stale docs: `Sexp::sym_id` (ids are the process's, in the arena's
    order) and `shared.rs`'s `symbol` (the arena's `new_symbol`).
- Tests:
  - `robigo-rtcore/src/fork_tests.rs`, not under Miri, one per lock:
    `LIVE_ISOLATES`, `ENV` exclusive, `ENV` shared, the arena.
    - Another thread holds the lock and releases it only once a fork has
      entered `prepare` (`robigo_heap::fork_prepares`), so the lock is
      provably held when the handlers run (S4).
    - The child starts an isolate, writes the environment through the
      `Sys.setenv` writer, interns a new symbol, and must exit 0 within
      20 s.
  - `robigo-rtcore/tests/fork_first.rs`: a fork before any heap exists
    runs `prepare`, so the constructor registered the handlers.
  - Negative control: with registration disabled (the constructor
    included), all five fail. The four children never finish, and
    `prepare` does not run before the first heap.
  - The heap's own fork test now says what it covers (heap-only users)
    and what it does not (the interleaving is the scheduler's).
