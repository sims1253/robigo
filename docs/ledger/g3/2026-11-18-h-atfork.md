## 2026-11-18: one set of fork handlers for the process's locks

- Why: two open findings.
  - #851's review: the symbol arena registered its `pthread_atfork`
    handlers lazily, inside its first lock (`Once::call_once`). A fork
    from one thread while another was inside that first `call_once` left
    the child's `Once` in progress for ever.
  - H's note on #842: B's `LIVE_ISOLATES` count and clib's `ENV` lock had
    no fork handlers at all. A child forked while another thread held one
    blocked on its first isolate start or end, or its first `Sys.setenv`.
- What:
  - `robigo-heap/src/fork.rs`: one `pthread_atfork` triple for the
    process.
    - It is registered before `main` by an `.init_array` constructor,
      while the process has one thread, so no fork can race the
      registration. `Core::new` calls the same registration in case a
      linker dropped the constructor. The registration is an atomic swap,
      not a `Once`, so a child never inherits an initialization in
      progress (Sol r1 S1).
    - `prepare` first takes `FORK`, a pthread mutex of its own that
      serializes whole forks, so two forks' handlers never interleave
      (S3). It then takes the embedder's locks, given by `set_fork_locks`
      (robigo-rtcore: `LIVE_ISOLATES`, then `ENV` exclusive), and last the
      arena's.
    - `parent` and `child` release in the reverse order, only what that
      `prepare` took.
    - The embedder's take and release are two plain atomics
      (`set_fork_locks`), with no "being set" state a fork could catch.
      robigo-rtcore stores them from an `.init_array` constructor of its
      own, before `main`, and again at the start of `with_options`, before
      `Registration::new` takes `LIVE_ISOLATES`. So no fork can find one of
      its locks held before the handlers know it (Sol r2 S7).
    - The module's doc holds the process's lock order, the one place it is
      written: `FORK`, `LIVE_ISOLATES`, `ENV`, the arena. It also says what
      `prepare` waits for, and why std's environment lock is not in the
      order.
  - **std's environment lock (S2).** `EnvWriter::set`/`unset`
    (`clib.rs`) call the C library's `setenv`/`unsetenv` under `ENV`
    exclusive instead of `std::env::set_var`.
    - So robigo never takes std's lock for writing. A child forked while a
      std reader (`std::env::var`: 67 sites in the rt crates, and
      `vars_os` in `Sys.getenv`) held it shared inherits a reader count
      that blocks only writers, and the child's `Sys.setenv` still writes.
    - The inversion with `std::process::Command`'s fork fallback, which
      holds std's lock shared across `fork`, is gone: no robigo thread
      waits on std's lock while it holds `LIVE_ISOLATES` and `ENV`.
      robigo-rt does not spawn through `Command`.
    - std's readers of one variable now run concurrently with the
      writer. They read through glibc's `getenv`, which glibc 2.41
      (`MIN_GLIBC`) makes safe against `setenv`.
    - A listing walks `environ`, which glibc does not make safe. So
      `Sys.getenv()` lists through `clib::env_vars`, which holds `ENV`
      shared, and `EnvWrites::assume`'s contract now says that nothing
      else walks `environ` (by hand or through `std::env::vars`) while an
      isolate may write. On an older glibc it says that no other thread
      reads the environment at all, `std::env::var` included (S6).
  - `arena.rs` loses its lazy registration and keeps `lock_for_fork` and
    `unlock_after_fork` for the triple. Its test guard
    (`hold_lock_for_test`) is an `unsafe fn` whose guard is neither `Send`
    nor `Sync` (S5).
  - `isolate.rs`: `fork_take` and `fork_release` hold the two guards in a
    static between the handlers. `FORK` guarantees one fork at a time.
  - `clib.rs`: `env_write_lock`, for the handlers. B's latest push made
    `env_locale` and `c_locale` take `ENV` shared, so `prepare` must take
    it exclusive, and does.
  - `docs/g3.md`: a note under L6. `ENV` and `LIVE_ISOLATES` are
    process-global by necessity (one environment per process), hold no R
    state, and are ordered in `fork.rs`.
  - Two stale docs: `Sexp::sym_id` (ids are the process's, in the arena's
    order) and `shared.rs`'s `symbol` (the arena's `new_symbol`).
- **Lazy process-global state (Sol r4 S9).** A `OnceLock` caught
  mid-initialization by a fork stays "running" in the child, and the
  child's first use of it waits for ever. Sol reproduced it with a shim
  that paused `heapsize::settings()`'s `getenv` across a fork.
  - `robigo_heap::once_excluding_fork(cell, f)` runs the initialization
    under `FORK`: no fork starts until the value is published, and an
    initialization waits for a fork already between its handlers. An
    initialized cell takes no lock, and an initializer that reaches another
    takes `FORK` once (a per-thread flag).
  - Every process-global lazy initializer that an isolate's start, an
    environment write or an install reaches uses it:
    - robigo-heap: `heapsize::settings`, `shared::shared`,
      `set_symbol_bits`, `gc.time`'s start instant;
    - robigo-rtcore: `clib`'s two C locales and `glibc_version`.
  - The order this creates (Sol r5 S10): such a cell's first read takes
    `FORK`, so it must not happen while the caller holds a later lock.
    `clib::env_writer` read the glibc version after taking
    `LIVE_ISOLATES`, so the first write could deadlock against a fork.
    It now reads the version first, and `arena::install` makes the shared
    objects before the arena's lock. The other call sites were checked:
    no `ENV` reader reaches a guarded cell.
  - Not converted: the other process-global cells in robigo-rt
    (`base.rs`'s `Bound` and `Wide`, `compile/crosscheck.rs`) and
    robigo-rtbuiltins (`subassign.rs`'s expand factor, `text.rs`,
    `grep/mod.rs` three times). A forked child that runs R code can reach
    them. They are outside the guarantee this PR makes (a child can start an
    isolate, write the environment and intern) and in other owners' files.
    The fix is the same one-line change: a follow-up.
- Tests:

  - `robigo-rtcore/tests/fork_env_write.rs`: one thread holds `FORK`,

  - `robigo-rtcore/tests/fork_first.rs`: a fork before any heap exists

  - `robigo-rtcore/tests/fork_first_isolate.rs`: 40 forks while another

## CI's hang on 96a7b6c55, and std's stdio locks (2026-11-21)

- **The failure.** CI's `rt` job (`ROBIGO_FRAME_QUARANTINE=1`, `-p robigo-rtcore --lib`) failed once: a child forked while the ENV lock was held never finished.
- **Reproduced.** The child now reports each step through a pipe. On a timeout, the parent reads its `/proc/<pid>/syscall`.
  - The release lib test binary was looped in 8 parallel streams, under quarantine. It hung 13 times in about 2,600 runs, spread across all four lock tests.
  - Every hang had the same signature: every step done (isolate started, environment written, symbol installed), then a futex wait on `std::io::stdio::STDOUT`+8, value 2, while the isolate dropped.
- **The cause.** The isolate's console (`console.rs:70`) flushes its `BufWriter<Stdout>` and its `Stderr` on drop. At the fork, libtest's main thread held std's stdout lock while it printed a result line.
  - Shipping code can be in the same state: any thread that writes through std's stdout or stderr while another forks. That covers another isolate's console, an embedder's thread, a warning and a panic message.
- **The fix.** `prepare` takes std's stdout lock, then its stderr lock, last in the order (after the arena). `release` drops them first (stderr, then stdout).
  - The order rule: no thread takes locks 0–3 while it holds one of std's stdio locks. No shipping rt path does.
  - std's stdin is not taken: a reader blocks for as long as its input takes.
  - `prepare` now waits for a write to finish. A write blocked on a full pipe holds the fork until the reader drains it.
- **Tests.**
  - Two lock tests: stdout held and stderr held.
  - Negative control: with the take disabled, the two hung in 9 of 10 runs, with CI's signature.
  - With the fix: 6,000 runs of the lib test binary under the same load, 0 failures.
  - One mutex now serializes every fork test (Sol S17).
- **The give-up path.** If the holder gives up after 2 s, or another test's fork releases it early, the lock is free when `prepare` takes it. The child then starts with it owned by its own thread. Only the test's overlap is lost, never the child, so that path cannot produce the hang.
- **Review.** Sol rounds 8 and 9, with gpt-6.2-sol on high: APPROVE.
  - S17 and S19 are fixed.
  - Kept as nits, for the next heap PR:
    - S14: the diagnostic maps (`ROBIGO_GC_PIN_REPORT`, `ROBIGO_GC_STRONG_DLL`) seed std's `RandomState`. Where seccomp denies `getrandom`, that seeding reaches std's `/dev/urandom` OnceLock. The fix: use `BuildFx` there.
    - S15: the blocked-pipe wait (documented above).
    - S16 and S18: test hygiene. `fork_first_isolate`'s watchdog still uses `eprintln!`; `waitpid` ignores EINTR.
- **Earlier review.** Round 6 (gpt-6.2-sol) resolved S1–S10, and round 7 approved with S11–S13 as nits:
  - S11: on an older glibc, a child counts the isolates of its parent's other threads;
  - S12: the S10 test depends on timing;
