## 2026-11-18: perf measures its own base instead of waiting for main's run

- **Why:** CI throughput (docs/ledger/g3/2026-11-18-ci-throughput.md, §3).
  On 2026-11-18, a pull request's `perf` job held a runner while
  scripts/perf-baseline.py waited for main's run of the merge's base to
  publish `perf-main`: 1,924 runner-minutes over 73 jobs, a median 23
  minutes. 31 of the 73 were cut off at 50 minutes and then compared with
  an ancestor, so main's own changes counted as the PR's. The foreman
  asked for a PR for the lead's sign-off.
- **What changes:**
  - A `perf-base` job (pull requests with the heavy jobs) builds the
    merge's base, HEAD^1, as `build` builds the candidate: the same image,
    the same rust-cache entry, robigo and the base-package natives. It
    runs beside `build`, not after it.
  - `perf` measures that base on its own runner with the candidate's filter
    (scripts/perf-select.py), then compares and confirms as before:
    perf.py, 0.5%, scripts/perf-paired.py.
  - **GNU R's records** (its answers, which decide `wrong`, and its counts
    for the ratio) used to come from main's artifact, measured on main's
    runner. They now come from a cache keyed by the oracle image, the CPU
    signature, the libc6 and valgrind packages and the measurement's
    inputs (benchmarks/**, scripts/perf.py). Main's run saves every record,
    failures included: GNU R fails on flexclust, flexclust_no_s4 and
    volcano in every run, and the old job inherited those failures too
    (their answers are not judged, as before). A pull request completes the
    records first (`scripts/perf-gnur.py fill`). It keeps the cached ones,
    measures GNU R for selected benchmarks without one, and measures a
    fresh failure once more so that a timeout does not become the oracle.
    A failure measured twice is accepted only for a benchmark that
    benchmarks/gnur-known-failures.txt names (the three above, with their
    reasons; main's run warns when they drift). Any other benchmark fails
    the job, as does a selected benchmark still without a record (Sol's
    round 2: two failures on one runner do not prove that main's record
    would have failed). Only then
    are the base and the candidate measured against these records (Sol's
    P1: a GNU R failure measured once on a miss must not let a wrong answer
    pass).
  - Main's per-commit run, its `perf-main` artifact (the history and the
    scoreboard) and its numbers do not change.
  - scripts/perf-baseline.py goes: nothing else used it.
  - **perf-rt** already worked this way: `perf-rt-build` builds main's
    robigo-rt from HEAD^1 itself, and `perf-rt` caches GNU R per CPU
    signature. It never waited for main.
- **At least as strict:** the same rows, the same filter, the same
  thresholds and the same paired confirmation. The direct comparison is
  now on one runner, not this runner against main's. The old compare step
  passed silently (`exit 0`) when no baseline was found within 30
  ancestors; there is always a base now.
- **Robigo's counts move with the length of its own path.** In validation
  the same binary run as `/data/cand/robigo` instead of `/data/old/robigo`
  (one character longer) counted up to 0.16% differently
  (reversecomplement_naive). So the base sits at `base/robigo`, as long a
  path as `dist/robigo`. The same binary at a path 7 characters longer
  counted up to 0.158% differently (reversecomplement_naive), with 4
  benchmarks over 0.05% (closures, reversecomplement_2, simple-internals).
  Today's paired confirmation (scripts/perf-paired.py) copies the two
  binaries to `<tmp>/base/bin/robigo` and `<tmp>/candidate/bin/robigo`, 5
  characters apart. That is a bias in the step that confirms a regression:
  under the 0.5% threshold, but not under the noise. The copies now go to
  `base/` and `cand/`.
- **Validation:** four recent pull requests, measured in CI's base image
  on one machine (callgrind instructions, all 93 benchmarks, every binary
  at a path of one length). The PRs are #847, #851 and #849 (G3, whose
  `robigo` did not change) and #802 (robigo-numerics). For each, the PR's
  CI binary was measured against:
  - the old job's base: main's `robigo` artifact. For #851, #849 and #802
    that was an ancestor's, because main's run of their base had not
    published yet;
  - the new job's base: HEAD^1 rebuilt in CI's rust image at CI's path.

  | PR | old job: max Δ | new job: max Δ | max abs(new Δ − old Δ) | flagged (>0.5%) old / new | CI reported (cross-runner): max Δ, flagged |
  |---|---:|---:|---:|---:|---:|
  | #847 | +0.0089% | +0.0341% | 0.0344% | 0 / 0 | −0.0107%, 0 |
  | #851 | +0.0099% | +0.0336% | 0.0333% | 0 / 0 | −0.0100%, 0 |
  | #849 | +0.0080% | +0.0335% | 0.0335% | 0 / 0 | +0.0149%, 0 |
  | #802 | +0.0118% | +0.0339% | 0.0338% | 0 / 0 | −0.0220%, 0 |

  Every verdict is the same: nothing flagged, as CI said.

  **The deltas agree to 0.034%, not to ±0.00% as asked.** That criterion
  cannot be met here by any method, the old one against itself included,
  for two reasons:
  - **Callgrind's own spread on this machine:** the same binary measured
    twice at the same path differs by up to 0.008% (#847, every one of the
    93 benchmarks moves a little). No method meets ±0.00% here, the old
    one against itself included.
  - **The rebuilt base is not byte-identical to main's artifact:** its
    `.text` and `.rodata` differ only by a C `__DATE__`/`__TIME__` (Nov 18
    here against Nov 13 in CI's cached objects), which moves the merged
    string table, and with it RIP-relative offsets. Section sizes,
    `.eh_frame`, `.data` and the symbol tables are equal. The largest
    differences are flexclust (−0.034%) and flexclust_no_s4 (−0.03%), in
    all four PRs alike; the next ones are up to 0.015% (#847: scalarWhile
    0.015%, pidigits 0.012%; the other PRs up to 0.014%), a little above
    the one repeat's 0.008%.

  What would make the counts exact is not done here: running callgrind
  with address randomization off, and a fixed `SOURCE_DATE_EPOCH`. Whether
  0.034% (under a tenth of the 0.5% threshold) is acceptable is the
  lead's call.

  In CI the second reason mostly goes away: `perf-base` restores the same
  rust-cache entry as `build` in the same run, so the base and the
  candidate carry the same cached C objects. The exception is a pull
  request that rebuilds the crate holding that C code, which gets a new
  date in the candidate only. The old job never had this: main's artifact
  came from main's own cache entry. A fixed `SOURCE_DATE_EPOCH` in both
  build jobs would remove the date entirely (GCC uses it for `__DATE__`
  and `__TIME__`). Not done here.
- Scripts and data: `~/.cache/robigo-research/a1/perf-val/` (validate.sh,
  measure.sh, compare.py).
