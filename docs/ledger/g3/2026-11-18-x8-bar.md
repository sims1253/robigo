## 2026-11-18: X8's bar: D12, growth by copy or by `mremap`

Written before any variant is built past a compile check, for the
foreman's signature in the pull request that adds this entry. Once a run
cites it, it is fixed. A change is a new dated entry that names this one
and why, and it is committed before the runs it governs (§15.2). It does
not replace D12's rule in `2026-11-17-m2m3-bars.md`: it fixes what each
variant is, the controls, the runs and the records.

### The question

GNU R's `EnlargeVector` (`R462/main/subassign.c:140-179`) keeps the same
object when it is not shared, growable and long enough. Otherwise it
allocates a new vector of `newlen × R_EXPAND_FRAC` (1.05) and copies.
Growing `x[i] <- i` to 1e6 elements reallocates about 280 times and copies
about 20 times the final size. g3.md §4 asks whether a large unshared
vector can move by remapping its pages instead of copying them.

### Variants

All three are on branches from one base SHA (main at the first branch's
creation), named in the run records.

- **`copy`** (`g3/x8-copy`): main. Large chunks come from `std::alloc`,
  and growth copies.
- **`mmap`** (`g3/x8-mmap`): a control, not a candidate. Large chunks (an
  object above `MAX_MEDIUM`, 64,464 bytes) come from `mmap` directly,
  64 KiB-aligned as today and freed by `munmap`. Growth still copies. It
  separates the allocator's change from the remapping.
- **`mremap`** (`g3/x8-mremap`): `mmap`'s chunks. `enlarged`
  (`robigo-rtbuiltins/src/subassign.rs`), for a source that is all of
  these:
  - a large chunk's object;
  - not shared (`MAYBE_SHARED` false: no other reference);
  - never handed to C (`SEEN_BY_C`): a C word could still hold its
    address;
  - not pinned or immortal;
  - of a type whose elements need no fill beyond its length (every
    vector type: the new tail is filled as today);

  moves the chunk's pages to a new chunk of the new capacity with one
  `mremap(old, old_len, new_len, MREMAP_MAYMOVE | MREMAP_FIXED |
  MREMAP_DONTUNMAP, new)`, where `new` is a 64 KiB-aligned range reserved
  first. `MREMAP_DONTUNMAP` leaves the old range mapped and empty, and
  `mprotect(old, old_len, PROT_NONE)` follows (see "What the remapping must
  keep"). Any other source copies, as `copy` does, and so does every source
  on a kernel that refuses `MREMAP_DONTUNMAP` (`EINVAL`: Linux before 5.7,
  or one that limits it to other mappings). Re-reserving the old range
  after an unmapping move (`MAP_FIXED_NOREPLACE`) is not used: another
  isolate's thread could take the range in between.

### What the remapping must keep

Each item is checked before any run, and a variant that fails one is
not measured.

- **Address relations.** GNU R's reallocation gives a new object at a new
  address, and its in-place growth keeps the object.
  - `MREMAP_FIXED` onto a fresh range always gives a new address, so
    an in-place extension cannot keep an address that GNU R changes.
  - **The old address stays reserved until the sweep that releases its
    account.** In GNU R the old vector stays allocated until the next
    collection, so no new object can have its address before then. After
    the move the old range stays mapped, empty and `PROT_NONE`. It is
    released (`munmap`) by the same sweep that takes its VECRECs out of
    `valloc` (below). Until then no allocation can receive it, and a
    stale pointer into it faults.
  - Tests:
    - in place keeps the `Sexp`, and reallocation changes it;
    - a large allocation made right after a growth never gets the old
      address before a collection;
    - the old range is `PROT_NONE` from the move to that sweep: checked
      in `/proc/self/maps`, and by a read in a forked child, which must
      die of `SIGSEGV`;
    - after the sweep the range is unmapped. robigo-rt registers neither `tracemem` nor
    `inspect` yet; C1-TM's `tracemem` cases add an R-level check in wave
    5.
- **GNU R's accounting.** GNU R counts the old vector until the next
  collection. The remapped-away object's VECRECs therefore stay in
  `valloc` (an account, with no memory behind it) until the next sweep,
  so the collection schedule and `gc()` are `copy`'s.
  - A test compares `gc()`'s table and the collection count after
    `growdbl.R` under both variants; they must be identical.
- **The heap's own records.**
  - The moved object is a fresh allocation to the collector, as GNU R's
    new vector is: the youngest generation, its age reset, and not in the
    remembered set (its old record, if any, goes).
    - Test: a list promoted to the old generation, grown by remapping
      while it holds young elements, keeps them live across a young
      collection (`ROBIGO_GC_MOVE=young:N`).
  - The old chunk leaves the chunk table as a reserved range awaiting its
    sweep, and the new one enters it, sorted.
  - `min_addr`/`max_addr` and the conservative scan's range include the
    new chunk.
  - The large-object header (mark word, `REMEMBERED_OFF`) is rewritten
    at the new base.
- **Precise roots.** At the move, the source is named only by the root
  slot that `enlarged`'s caller passes in. That is the binding's root in
  `x[i] <- v` / `x[[i]] <- v` (`subassign.rs`'s `EnlargeVector` callers),
  which roots the vector it is enlarging; the source is unshared, so no
  other binding, list element, promise value, VM slot or barrier record
  names it. Between the move and the caller's write of the result into
  that slot there is no safepoint:
  - the move and the write are in one `&Cx` build, which cannot collect
    (H2);
  - the write follows the build before any `&mut Cx` call.

  A call site where this cannot be shown copies. Check: a debug-only
  hook (`ROBIGO_X8_COLLECT_AT_MOVE=1`) that runs a full collection right
  after the move, with the caller's roots as they are, must find no
  root, slot, promise or barrier record naming the source (each is
  compared with the source's address, which panics on a match). It runs
  as a step of the variant's rt-ci.
- **Failure of the syscalls.** Neither `mmap` nor `mremap` failing is
  ever an abort. `ENOMEM` includes `vm.max_map_count`, a limit
  `std::alloc` does not meet at the same point.
  - A failed `mremap` falls back to the copy.
  - A failed `mmap` takes GNU R's allocation-failure path: collect,
    retry, and GNU R's message, through `Cx::refused_again` once #874 is
    in.
  - Both get injected failures in rt-ci's injected-failures step
    (`scripts/rt-fail-alloc.py`): a knob that refuses the n-th `mmap` or
    `mremap`.
  - Mappings: `mmap` uses one mapping per large object, as glibc's large
    `malloc` does. `mremap` holds two per large object between a move and
    its sweep (the new range and the reserved old one), so at most one
    more per object moved since the last collection.
- **Gates.** The variant passes the full `scripts/rt-ci.py` (gctorture,
  `ROBIGO_GC_MOVE=1` and `young:N`, PIN_REPORT, NO_INPLACE, MATERIALIZE,
  FRAME_QUARANTINE, the small vector limit, injected failures, overshoot,
  retry torture), and Miri on rtcore and heap's non-FFI tests.
  - Under Miri, remapping is compiled out (`cfg(miri)`), because Miri has
    no `mremap`; the variant is then `mmap`'s.

### Workloads and modes

- **Programs** (wall time and peak RSS):
  - `rt/mem/growdbl.R`: `x[i] <- i` to 1e6;
  - `rt/mem/listgrow.R`: `l[[i]] <- x` to 2e5;
  - `rt/mem/cappend.R`: the control, a new vector at every step;
  - `rt/mem/churn.R`;
  - `suite/binarytrees.R` and `suite/fib.R` (SUITE).
- **Rows** (instructions; wall time with §13's harness):
  - GROWTH: `grow-dbl`, `grow-list`;
  - CALLS: `plain`, `defaults`, `named`, `env-fn`, `superassign`, `s3`;
  - SUITE: `fib`, `binarytrees`;
  - E7: `e7-paste`, `e7-match`, `e7-unique`.
- **Modes:** every rule holds with inlining on (the default) and with
  `ROBIGO_NO_INLINE=1`.

### Runs

- **Binaries:** one release build per variant (`cargo build --release
  --locked -p robigo-rtapi`), each in its own checkout and target, with
  its sha256 and GNU build ID recorded. The same binaries run on both
  machines; their glibc is 2.44 on both.
- **Wall time:** §13's protocol, with the cycles study's harness
  (`data/2026-11-16-cycles-study/study-wall.py`) until A3 moves it into
  `scripts/`.
  - A sample is (T(2K) − T(K)) / K. K is sized so that a run takes at
    least 0.3 s, above D12's protocol's 0.05 s.
  - 11 interleaved rounds over every (binary, program or row), the order
    rotated each round and K against 2K alternated; medians compared.
  - On the desktop (AMD Ryzen 9 5900X, WSL2) and on m0pad (AMD Ryzen 5
    PRO 5650U, CachyOS).
  - m0pad is idle: no build and no other agent's run during the rounds.
    Its load average is recorded before and after; a run above 1.0 is
    repeated.
  - The harness: `scripts/wall13.py` (#873) if it is on main when the
    runs start, else the cycles study's `study-wall.py`. The records name
    which, and its SHA.
- **Peak RSS:** `scripts/rss.py --runs 5`, the median; all five runs of
  each binary are recorded.
- **Instructions:** `scripts/perf.py rt-bars`'s method (N against 2N,
  callgrind), twice per binary and mode, on the desktop.
- **Estimated cycles:** the pinned model, reported only.
- **Allocations:** `ROBIGO_GC_STATS=1`, per program.

### Rule

D12's, from `2026-11-17-m2m3-bars.md`, unchanged. `mremap` wins only if
all of these hold:

- `growdbl.R` and `listgrow.R` are at least 10% faster in wall time than
  `copy` on both machines, in both modes;
- no GROWTH or MEM program's peak RSS is higher than `copy`'s. Higher
  means that `mremap`'s median exceeds `copy`'s median by more than
  `copy`'s own range over its five runs (max − min). D12's tie band
  covers only instructions and wall time;
- no other row or program is worse than `copy` beyond the tie (±1%
  instructions or ±2% wall time), in either mode, on either machine;
- the address relations and the accounting above hold.

`mmap` decides nothing.
- If `mremap` wins, `mmap`'s numbers show how much of the gain the
  allocator change alone gives.
- If `mmap` alone is faster than `copy`, that is a finding for a later
  entry, not a decision here.

Inside the tie, `copy`, named first, wins. The loser branches are deleted
after the decision PR, and their binaries after the ledger records them.

### Machine state

Each machine's records hold `vm.max_map_count`, `vm.overcommit_memory`,
and transparent huge pages (`/sys/kernel/mm/transparent_hugepage/enabled`
and `defrag`). No variant calls `madvise`: if one needed it, all three
would make the same calls.
