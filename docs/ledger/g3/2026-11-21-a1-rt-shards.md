## 2026-11-21: the rt job in three shards

- **Why:** the one `rt` job ran every step of scripts/rt-ci.py in 29-38
  minutes against a 40-minute limit. #900, on the critical path, was
  cancelled at 40 minutes inside the last step. #907 raised the limit to 60
  as a stopgap; this is the fix.
- **The steps' times** (main's 2f16dc4c, run 44607483451, the rt-ci.py
  step 35.3 min):

  | step | min |
  |---|---:|
  | release tests (8.4 of it the release build, the tests about 20 s) | 8.75 |
  | conformance under ROBIGO_GC_MOVE=young:16 with gctorture | 10.00 |
  | conformance under ROBIGO_RETRY_TORTURE=1 (its feature rebuild and run) | 6.66 |
  | conformance under gctorture | 4.15 |
  | builtin differential (23 rows; about 5 with #887's 87 rows and plant build) | 1.70 |
  | ROBIGO_GC_MOVE unit tests with gctorture | 0.79 |
  | the other 15 steps | 3.7 |

- **The split** (the foreman's choice, option A: three shards, no runner
  change):
  - `rt` (modes): the release build and tests, the conformance and its
    observation modes, gctorture, quarantine, pin report, stress,
    overshoot, E9, the byte-code crosscheck: about 16 min, then L1's rdb
    round trip. Timeout 35.
  - `rt-gc-move`: the moving collector's unit tests and conformance:
    about 19 min (8.4 build, 10 conformance). Timeout 40.
  - `rt-feature-builds`: the builtin differential with its plants, and
    retry-torture: about 15 min now, about 20 after #887. Timeout 40.

  The wall time goes from 35 to about 19 minutes, for about +17
  runner-minutes per run (two more builds).
- **Measured** in #910's first run (fd52c010d): `rt` 15.7 min,
  `rt-gc-move` 16.7, `rt-feature-builds` 9.1 (with #863's 23 builtin rows;
  #887's 87 and its plant build add about 4). The wall time is 16.7
  minutes, from one job of 29-38. Timeouts are about twice those: 35, 35
  and 30.
- **Not chosen:** five shards, with the GC_MOVE conformance itself halved,
  would give about 15 minutes. That needs a `ROBIGO_CONF_SHARD` in the
  conformance runner and about +34 runner-minutes per run. 19 minutes is
  already under the other long jobs, so it would not shorten a PR's cycle.
- **What a shared build would save** (recorded, not built): one job builds
  the release test binaries once and the shards download them. That would
  save the two extra 8.4-minute builds, about 17 runner-minutes per run,
  and about 8 minutes of each shard's wall time, so `rt-gc-move` would take
  about 11 minutes. The cost: an artifact of the test binaries and
  robigo-rt (`target/release/deps` of the rt crates, several GB with debug
  info), which has to upload and download inside the budget. The 134 MB
  `builtin-diff-data` artifact stalled once on upload (#887).
- **Mechanics:**
  - `rt-ci.py --shard NAME` runs one shard's steps, in rt-ci.py's order,
    and without `--shard` a local run is unchanged.
  - Each step's shard comes from one rule, `shard_of`. The R_HOME tree (3
    s) is made in every shard; every other step is in exactly one
    (scripts/test-rt-ci.py).
  - Every shard prints its steps' wall times, slowest first, when it ends,
    whether it passed or not.
  - Only `rt` saves the rust cache and the R tarball cache, so two jobs
    never race to save one key.
  - ci-check.py lets the two new jobs be skipped only as `rt` is (rt mode
    false), and `Check` needs them.

## Later on 2026-11-21: five shards, with budgets

By run 44883150235 (main with #887's 90 builtin rows and #899's poison-dead
steps) `rt` took 29.2 minutes of steps (timeout 35) and `rt-feature-builds`
25.3 (timeout 30; one run was cancelled at 30). Since #910's run 44865825323
the crates' test build went from 8.5 to 11.6 minutes (paid in `rt` and
`rt-gc-move`), retry-torture's conformance from 6.3 to 12.8, the builtin
differential from 2.3 to 7.2, GC_MOVE young:16's conformance from 7.0 to
11.1, gctorture's from 3.8 to 5.6, and `ROBIGO_MATERIALIZE=1` from 0.14 to
6.5: its `cargo test -p robigo-rt` alone no longer turned on
robigo-rtcore's dev-dependency feature `robigo-heap/test-support` (#894), so
cargo rebuilt heap and every crate above it. #924 raised both timeouts to 60
as a stopgap.

The rebalance (the rt-debug-assertions PR):
- the MATERIALIZE step runs over every rt crate, as the other mode steps
  do, and so reuses the release tests' build;
- GC_MOVE's crate tests (9 tests, about a minute) move into `rt`, which
  has the crates' test build; `rt-gc-move` no longer pays an 11.6-minute
  build for them and becomes `rt-gctorture`: the two long conformance runs
  under gctorture, plain (out of `rt`) and with GC_MOVE=young:16, on a
  conformance build only;
- the builtin differential gets a job of its own, `rt-builtin-diff`, with
  builtin-diff-data's records; `rt-feature-builds` keeps retry-torture and
  the poison-dead steps;
- `rt-debug-assertions` is the fifth.
- Each shard has a budget in rt-ci.py's `BUDGETS` (its measured time plus
  20%, rounded up, with where and when it was measured); the end-of-log
  table warns at 90% of it, and each job's timeout is twice it
  (scripts/test-rt-ci.py pins the three relations).
- **Next:** the shared build artifact (above) is no longer a note: the
  test build grew 3 minutes in two days and is paid in three shards.

## Later on 2026-11-21: the crates' tests in the quick profile

A cold build of the six rt crates' test targets (`cargo test --no-run
--timings`, -j6, a fresh target directory): 766 s on the release profile
(4,551 s of unit time; robigo-rt's 21 test units 2,360 s, about 112 s each)
against 106 s in `quick` (524 s; robigo-rt's 80 s, 3.8 s each). With
release's `lto = "thin"` and `codegen-units = 1`, each of the ~64 test
binaries makes its own whole-program pass. Their run: 19.8 s in `quick`,
20.3 s on release. `quick`'s `incremental = true` costs a cold build 147 s
and 2.3 GB against 101 s and 1.6 GB without (rust-cache sets
`CARGO_INCREMENTAL=0` in CI); no separate profile was worth it.

- The crates' tests, and every mode step that runs them, use `quick`.
  Everything that judges the binary users get stays on release.
- `rt-release-crate-tests` runs the crates' tests on the full release
  profile, on main's push runs only (with #927, one runs and one waits), so
  a codegen-dependent crate-test failure is found after the merge, within
  one main run. That is the accepted trade.
