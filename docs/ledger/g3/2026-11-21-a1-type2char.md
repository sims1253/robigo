## 2026-11-21: type2char's unknown types, and one R_typeToChar

- **Why:** two deferred lows in A1's notes.
  - robigo's `type2char` said "unknown type", with no number and no
    warning, where GNU R's (util.c) warns "type N is unimplemented in
    'type2char'" and says "unknown type #N".
  - `R_typeToChar` had two copies, rtapi's `r_type_to_char` and
    rtbuiltins' `type_to_char`.
- **What a code from outside reaches:** robigo-rt's objects always have a
  named type, so only a code that C passes in can be unknown.
  - `allocVector` truncated the code to 255 and said "invalid type/length
    (unknown type/1)". GNU R warns, then says "invalid type/length
    (unknown type #30/1) in vector allocation".
  - `coerceVector` already had its own copy of the warning and the number.
- **What changes:**
  - **`type2char_warn(cx, code)`** (u32: the C API's `SEXPTYPE` is an
    unsigned int) gives GNU R's warning and "unknown type #N". Both C entry
    points use it, `allocVector` naming the caller's code, not a truncated
    one.
  - **`type2char`** stays infallible for robigo-rt's own types. Both
    functions read one table, `type_name`.
  - **rtapi uses rtbuiltins' `type_to_char`.** The two copies agreed,
    because `type2char(OBJSXP)` is "S4".
- **`coerceVector` below 256 too** (Sol's round 1): codes 11, 12 and 26 to
  31 have no name either, and coerceVector only sent codes over 255 to its
  warning. Now `type2char` itself says "unknown type #N", so every message
  that names a target has GNU R's text. `Rf_coerceVector` gives the warning
  first exactly where the coercion's error will name the target
  (`coerce::vector::error_names_target`, which follows the kernel's
  dispatch). It does not for:
  - an environment ("environments cannot be coerced to other types");
  - an S4 object or a package ALTREP vector, which robigo-rt refuses as
    not implemented yet before its dispatch (GNU R takes the data slot or
    calls the method, and may go on from there);
  - a vectorizable pairlist or list to a type allocVector accepts but the
    coercion does not fill: a call, NULL, or intCHARSXP (73; Sol's rounds 2
    and 3).

  The order matters under `options(warn = 2)`, where the warning becomes
  the error.
- **coercePairList's and coerceVectorList's vectorizable branches** (the
  list's from Sol's round 3): GNU R allocates
  `allocVector(type, n)` first. robigo said "unimplemented type 'pairlist'
  in 'coercePairList'" for every non-atomic target; GNU R gives:
  - allocVector's "invalid type/length (closure/1) in vector allocation"
    for a type it cannot allocate (closure, symbol, an unnamed code, ...);
  - its CHARSXP error;
  - UNIMPLEMENTED_TYPE only for what it allocates but does not fill (a
    call, NULL).
- **Tests:** crates/robigo-rtapi/tests/capi.rs
  `coerce_vector_to_an_unnamed_type_warns_as_type2char_does` (atomic,
  environment, pairlist to an unnamed and to a named target) and
  `alloc_vector_of_an_unknown_type_names_the_callers_code`. It uses 30
  (NEWSXP, in GNU R's table without a name, so its result is defined) and
  999, plus a named type (builtin) that keeps its name with no warning.
