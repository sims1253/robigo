## 2026-11-23: the local slot pool, for builtin-diff and the crates' tests

#982 gave local gates one machine-wide pool of conformance case slots.
#989 adds builtin-diff's robigo-rt drivers and rt-ci's crate-test steps to it
(`scripts/conf_slots.py`).

**Known, not fixed: the default slot count ignores a cgroup CPU quota.**
- Without `ROBIGO_CONF_SLOTS`, the Python tools count the CPUs in the
  process's affinity mask.
- The Rust runner's `available_parallelism` also caps that by a cgroup CPU
  quota. Under a quota the two counts differ.
- This does not break correctness. The slots are the same files, so the
  side with the lower count only ever takes fewer of them.
- This box has no quota and CI has no pool, so it is not worth code now
  (Sol's deferred finding on #989; the foreman's ruling).

**The crate-test thread floor.** A crate-test step runs with
`--test-threads=max(held, 4)` (rt-ci.py's `CRATE_TEST_MIN_THREADS`), and it
never waits for more slots than its first.
- In #989's local gate, at load about 20, five crate-test steps got one
  slot each.
- The debug-assertions shard's crate tests ran at one thread for 3.0 min,
  so the shard took 5.5 min, 110% of its 5-minute budget.

**The threads were not what cost the time.** I timed the same step again
with its tests built beforehand, alternating one and four threads at load
24 to 32:

| `--test-threads` | run 1 | run 2 |
|---|---|---|
| 1 | 0.53 min | 0.71 min |
| 4 | 0.56 min | 0.59 min |

- The 3.0 min in the gate was the step's own build under load, which
  happens before any test runs and is not set by `--test-threads`.
- A floor is worth keeping only for long test runs. The foreman's rule:
  measure that case, and keep the floor only if four threads beat one by
  more than the spread between runs.

**The case the floor is for.** The longest gctorture crate-test step is
`ROBIGO_GC_MOVE` (move every movable object at every collection). I timed it
the same way, built beforehand, alternating thread counts:

| `--test-threads` | run 1 | run 2 | mean |
|---|---|---|---|
| 1 | 1.72 min (load 18) | 1.86 min (load 34) | 1.79 |
| 4 | 1.57 min (load 16) | 1.21 min (load 20) | 1.39 |

- Every four-thread run was faster than every one-thread run.
- The difference between the means is 0.40 min. The spread between runs is
  0.14 min at one thread and 0.36 min at four.
- So the floor stays, with these numbers. The comment at rt-ci.py's
  `CRATE_TEST_MIN_THREADS` cites them.
- The loads were not matched: the second pair ran at 34 and 20. The margin
  over the spread is small.

**The build is its own step now.** Each shard builds its crate tests' binaries
(unit and integration tests) in a step of their own before the first step
that runs them (rt-ci.py's `builds_first`). The run's line still holds the
doctests' compilation and, in a local run, its wait for a slot.

## 2026-11-23: rt-ci's shard budgets, remeasured

Each budget is the slowest of main's three runs of 2026-11-23 (45104024474,
45106626186, 45108072544), plus 20%. The `modes` rebalance is **not made**.

**The 20-job cap.**
- Moving steps into `gctorture`, or splitting it, would put more on the
  longest rt job, or add a job to every run.
- This account's hosted runners have a cap of 20 jobs at once. Over the
  1,638 jobs that ran from 2026-11-22 12:00 UTC to 2026-11-23 06:00 UTC:
  - 931 started at exactly 20 running;
  - every one of the 500 jobs that queued for more than 5 min waited while
    18 to 21 jobs ran;
  - the peak was 25 running, which includes `ubuntu-latest` jobs.
- An rt-mode run has 16 jobs (median; 85 runner-minutes), and a heavy run
  36 (185).
- So every extra job in a run makes every run's queue longer.

**Why the three single-build shards grew past their old budgets.** All three
budgets were set from #952's run 44927530340 (2026-11-21), or main's
44931071167 for release-crate-tests. Since then, from 1f8cc8fbb to
114113d6e:
- the rt cases went from 531 to 598 (+13%), and the ratcheted `tests/r`
  cases from 160 to 163;
- the rt crates' tests went from 596 to 647 (+9%), and their code from
  146,430 to 153,644 lines (+4.9%).

| shard | the one build | old budget (measured) | now, slowest (other two runs) | budget |
|---|---|---|---|---|
| `feature-builds` | robigo-rt with `retry-torture` and `poison-dead`, built twice: release for its two conformance runs, quick for robigo-rt's tests | 12 (9.87) | 13.30 (11.01, 12.66) | 16 |
| `release-crate-tests` | the crates' tests on the full release profile (thin LTO, one codegen unit); main's push runs only | 12 (9.82) | 14.03 (10.26, 10.19) | 17 |
| `builtin-diff` | the release robigo-rt and its `diff-plant` twin | 9 (7.42) | 9.34 (8.01, 7.49) | 12 |

- **What grew:**
  - `feature-builds` runs the larger rt case set twice.
  - `release-crate-tests` builds 9% more tests under LTO.
  - `builtin-diff` gained its digests (#981) and one row (100 to 101).
- **Unchanged:** `debug-assertions` stays at 5 min. Its CI runs took 2.58
  to 3.85 min; only local gates ran over, where the build happened under
  load.
- **The trend to watch:** a later rise of `feature-builds` or
  `release-crate-tests` beyond the case and test counts above is the
  shards' own growth.
